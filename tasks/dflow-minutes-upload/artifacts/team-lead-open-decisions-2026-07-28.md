## 1. 회신문 전달 — 누가, 언제 D'Flow에 보내나

**무엇을 정해야 하나**: `ddobak-reply-2026-07-27.md`(175행, 정본 §7 11건 전항목 답변 + 신규 발견 N5·N6 + 요청사항 6건)를 누가 D'Flow에 전달하고 언제 보낼지.

**왜 지금 필요한가**: ⚠️ **이유가 바뀌었다.** 초판은 "계약 v2.4를 받아내기 위해"를 최우선 이유로 들었으나, v2.4는 이미 소스에서 확보했다(항목 2). 지금 이 문서를 보내야 하는 진짜 이유는 셋이다 — ① **R1~R3 배포 일정 확인 요청**(회신문 §5) — 지금 유일한 실질 차단인 항목 3의 답을 받을 유일한 채널이다 ② **N5·N6 claim 오매칭 위험 통보**(항목 5) ③ 지금까지의 결정·§8~§10 반영 확인. ⚠️ **주의**: 회신문 「또박또박이 D'Flow에 요청하는 것」 4번("계약 v2.4 송부 — `ddobak-W18`이 대기 중입니다. 이게 없으면 저희 3차 착수가 불가합니다")은 **이제 사실과 다르다** — v2.4는 이미 소스에 존재하고, 3차(`W12`·`W13`) 착수는 계약 결핍으로는 더 이상 막혀 있지 않다(항목 2). 이 회신문 파일 자체를 고치는 것은 이 문서의 권한 밖이지만, 그대로 보내면 D'Flow에 낡은 전제("아직 계약이 없다")를 전달하게 된다.

**선택지**:
- (a) 팀장이 직접 D'Flow 담당자(PMO)에게 전달 — 회신문 4번 문구를 그대로 보내거나, 전달자가 "v2.4 원문은 브랜치에서 확인했습니다, 정식 송부만 부탁드립니다"로 갱신해 보낸다
- (b) 개발 측이 기존 커뮤니케이션 채널로 전달(⚠️ **채널 자체가 확인 안 됨** — 이전 왕복이 어떤 경로로 이뤄졌는지 자료에 명시가 없다)

**개발 측 권고**: 전달 경로는 팀장 소관. 다만 **회신문 4번 문구는 보내기 전에 갱신을 권고**한다 — 그대로 보내면 D'Flow가 이미 만든 문서를 다시 만들라는 요청으로 읽힐 수 있다(항목 6의 확인 요청을 대신 얹는 것도 방법, 하단 참조). **이 문서가 안 보내지면 항목 3(R1~R3 일정)의 답도 못 받는다** — 지금은 이것이 가장 큰 이유이며, 우선순위 1순위로 처리 권고.

**기한·소유자**: ⚠️ 확인 필요 (전달자 미지정)

## 2. 소스 기준 선행 진행 승인 — 계약 정식 송부를 기다리지 않고 착수해도 되나 (구: "계약 v2.4 미수령")

**무엇을 정해야 하나**: ⚠️ **성격이 완전히 바뀌었다.** 초판은 "D'Flow가 계약서 v2.4를 언제까지 보내도록 요청·독촉할지"를 물었다. 하지만 **v2.4는 이미 존재한다** — D'Flow 소스 브랜치(`origin/feat/minutes-folder-path`, 커밋 `f0d0b62`→`94e5eca`, `/Users/jji/project/wbs-web`)의 `docs/design/dflow-minutes-upload-api-spec.md`가 스스로 "버전: v2.4(2026-07-27) … ⚠️ 또박또박 송부본은 이 v2.4다"라고 선언한다(`dflow-source-findings-2026-07-28.md` §5). **독촉할 문서가 없다** — 남은 건 "정식 송부"라는 행정 절차뿐이고, 개발 측은 그걸 기다리지 않고 소스 기준으로 이미 진행 중이다. 그러니 이제 정할 것은: **정식 송부를 기다리지 않고, 확인된 소스 사본을 근거로 `ddobak-W18`(계약 사본 동기화)·`W8`(배지)·`W12`·`W13`(재편철 배치 코딩) 착수를 승인할지**다.

**왜 지금 필요한가**: 착수를 막던 두 가지 이유(계약 문언 부재, 소스 접근 불가) 모두 소스 조사로 해소됐다 — `W12`·`W13`에 필요한 배치 엔드포인트 스펙(요청/응답 스키마, 조상 규칙, 에러 처리)을 소스에서 전량 확인했고(`dflow-source-findings-2026-07-28.md` §2), v2.4 계약 문언과 실제 D'Flow 구현 사이에 위치·값 서술의 불일치도 발견되지 않았다(`dflow-contract-v23-delta-2026-07-28.md` §2-2). **다만 소스는 계약이 아니다.** D'Flow 자체 인수인계 문서가 "런타임 스모크 미실시"·"main 미머지"를 명시하고 있어(`dflow-source-findings-2026-07-28.md` §5), D'Flow가 정식 송부 전에 브랜치를 추가로 고칠 가능성이 남아 있다. 그 경우 소스 기준으로 짠 우리 구현이 **드리프트**한다. 이 리스크를 감수하고 진행할지가 지금의 진짜 결정 사항이다. ⚠️ **미배포는 이제 문서 진술이 아니라 실측으로도 재확인됐다** — 2026-07-28 D'Flow 운영 API(`GET /minutes?include_archived=true`, GET 전용) 조회 결과 응답 41건 `items[]`에 `archived` 키가 **없다**(v2.3 신설 필드). 즉 운영은 아직 v2.2 이하이고 브랜치는 실제로 배포 전이다 — 드리프트 리스크가 이론이 아니라 "지금도 진행 중인 상태"임을 뒷받침한다.

**선택지**:
- (a) **소스 기준으로 지금 착수** — `W18`·`W8`·`W12`·`W13` 전부. 이득: D'Flow 정식 송부 시점(날짜 미확정, 항목 3 참조)을 기다리지 않고 진행 가능. 손실: D'Flow가 정식 송부 전 코드·계약을 더 고치면 드리프트가 생긴다. 완화책: 착수 기준 커밋(`94e5eca`)을 레퍼런스로 고정 기록해 두고, 정식 v2.4 수령 시 diff 1회 대조를 **재편철 1회차 APPLY 전**에 의무화한다(dry-run까지는 드리프트가 있어도 되돌릴 수 있다)
- (b) **정식 송부 대기** — 드리프트 리스크는 없지만, D'Flow 인수인계 문서에 "배포 후 §4 통보"라고만 돼 있어 순서만 있고 **날짜가 없다**(`dflow-source-findings-2026-07-28.md` §「소스로도 확정 못 한 것」) — main 머지·배포 자체도 아직이라 무기한 대기가 될 위험이 있다

**개발 측 권고**: (a), 조건부. 근거: v2.4가 반영한 9건(정본 §2-E A~I)을 v2.4 원문과 `decisions-final` 원문 요지로 대조해 "취지가 다르게 반영된 것 0건"을 확인했다(`dflow-contract-v23-delta-2026-07-28.md` §2-1) — 소스가 신뢰할 만한 근거임을 뒷받침한다. 조건: ① 착수 기준 커밋(`94e5eca`)을 기록해 둘 것 ② 정식 v2.4 수령 시 diff 1회 대조를 재편철 1회차 APPLY 전에 반드시 수행할 것 ③ §2-E ⑥처럼 "소스는 해소돼 보이지만 D'Flow가 인지했는지 불확실한" 항목은 회신문에서 별도 확인(항목 6).

**기한·소유자**: ⚠️ 확인 필요 — 승인만 나면 착수는 즉시 가능(개발 측 소유). 승인 없이는 착수하지 않는다(현 상태).

## 3. D'Flow R1~R3 배포 일정 확보 — 소유자 (⚠️ 지금 유일한 실질 차단)

**무엇을 정해야 하나**: D'Flow의 R1(플래그 `false` 배포)·R2(플래그 `true` 전환)·R3(연결 초기화) 각각의 확정 날짜를 누가 받아올지.

**왜 지금 필요한가**: 계약 결핍(항목 2)이 해소되면서 **이제 배포 일정만이 유일하게 남은 실질 차단이다.** 정본 §0에 "R1은 검증 종료 즉시 배포(**날짜 미확정** — 확정되면 별도 통보)"라고만 돼 있고(`decisions-final-2026-07-27.md`), 소스 조사도 이를 넘어서는 정보를 주지 못했다 — D'Flow 브랜치는 `origin`에 푸시만 됐고 `main` 미머지, 자체 인수인계 문서가 런타임 스모크 0건임을 명시한다. **git 이력만으로는 실배포 여부를 실측할 수 없었으나**(`dflow-contract-v23-delta-2026-07-28.md` §3-4), **2026-07-28 D'Flow 운영 API를 직접 조회해 미배포를 실측으로 재확인했다** — `GET /minutes?include_archived=true`(GET 전용) 응답 41건 전부에 `archived` 키가 없다(v2.3 신설 필드이므로, 있어야 정상). 즉 **"오늘 기준 아직 미배포"는 더 이상 추정이 아니라 확정 사실**이다. 다만 이건 "아직"이라는 사실만 확증할 뿐 **언제 배포되는지는 여전히 미정**이다 — 이 항목이 요구하는 일정 확보 자체는 그대로 유효하다. 재편철 1회차 dry-run·APPLY는 배치 엔드포인트(`dflow-W6`)가 R1 신규라 R1 배포 전엔 실행 자체가 안 되고, `ddobak-W14`의 `include_archived` 동작도 R1 배포 전엔 실사용 검증이 안 된다(회신문 5번 "R1 배포 일시 통보" 요청과 동일 사안). ⚠️ 참고: 배치 엔드포인트는 **플래그와 무관하게 항상 활성**이라(`dflow-source-findings-2026-07-28.md` §4, `decisions-final` §3 배포 순서 정본과도 일치), R2(플래그 전환)까지 기다릴 필요는 없다 — 하지만 **R1이 실제로 서버에 배포**돼 있어야 하는 조건은 그대로다. 코드·계약이 준비돼도 서버가 안 떠 있으면 전부 무용하다.

**선택지**:
- (a) D'Flow의 별도 통보를 기다린다(수동)
- (b) 팀장이 D'Flow PMO 카운터파트에게 직접 일정을 확인한다(능동)

**개발 측 권고**: (b), 그리고 **지금은 이것이 최우선**. 재편철 1회차·2차 배포 창(#4)이 전부 이 날짜에 종속돼 있고, 계약·소스 조사로 더 밝혀낼 수 있는 것이 남지 않은 지금은 이 일정만 정해지면 실행이 곧바로 시작된다.

**기한·소유자**: ⚠️ 확인 필요

## 4. 2차 배포 창(R2 시점) — 이미 완성된 작업이 대기 중

**무엇을 정해야 하나**: 커밋 `d0b893e7`(또박또박 2차 선구현 — 제목 접두 폐기·team 완화·폴더명/깊이 검사, `W2`·`W3`·`W4`·`W5`·`W6`)을 **언제 `main`에 머지·배포할지**를 결정하는 기준점(R2 시점)을 D'Flow와 언제 맞출지.

**왜 지금 필요한가**: 이 커밋은 **이미 완성돼 검증까지 끝났지만 배포가 금지된 상태**다(`handoff-2026-07-27.md` "⛔ `d0b893e7`은 2차분이라 `main`에 올리면 안 된다... D'Flow R2 전에 나가면 제목 접두도 없고 폴더도 안 잡힌 상태가 된다"). R2 이전에 배포하면 회귀가 발생하는 반면, R2가 언제인지는 #3(D'Flow 일정)에 종속돼 있다. 완성된 자산이 대기 상태로 오래 머물수록 브랜치 드리프트·재검증 비용이 커진다.

**선택지**:
- (a) #3이 해소될 때까지 대기(현재 상태 유지)

## 5. 정책 판단 — `claim` 오매칭 위험 대응 (N5·N6)

**무엇을 정해야 하나**: 실측이 드러낸 두 가지 위험에 대해 운영 정책을 확정할지.
- **N5**: `dflow_synced_at`이 비어 있는데 이미 D'Flow에 연결된 회의가 4건 있다(id 36·38·45·87 — `meeting_dflow_controller.rb#claim`이 `dflow_url`만 갱신하고 `dflow_synced_at`은 안 채우는 정상 동작의 부작용). 향후 자동 링크(4차)가 이 4건을 "한 번도 안 올라간 회의"로 오판하면 **다른 회의록에 재연결 → 고아 + 오매칭**이 생긴다.
- **N6**: `claim` 오매칭이 **이미 실제로 1건 발생**했다(`id 34` 건). 정본 §6("자동 링크 v1은 자동 claim을 끄고 사람 승인만 허용")의 근거가 실증됐다.

**왜 지금 필요한가**: 급하지 않다 — 4차(`ddobak-W15`·`W16`, 자동 링크)는 D'Flow R3(연결 초기화)가 먼저 나와야 착수 가능해 아직 멀었다. 하지만 **지금 명문화해 두지 않으면 4차 착수 시점에 다시 논쟁**이 된다.

**선택지**:
- (a) 정본 §6의 "자동 claim 금지, 사람 승인만" 결정을 **그대로 4차 착수 조건에 못 박는다** — 추가 조치 없음(이미 정본에 있음, 재확인만)
- (b) (a)에 더해, 현재 `claim`으로 연결된 5건(N5의 4건 + 삭제된 id 34) 전체를 **4차 착수 전에 미리 사람이 재검증**한다(`id 34` 건은 이미 오매칭 확정. `id 87`(`260721 글로벌영업담당 임원 인터뷰_AS-IS` ↔ D'Flow `..._통합`) 건은 동일성 미확인 상태로 남아 있다 — 관련 수작업 트랙은 중단됐으나 재검증 대상에서 빠지는 것은 아니다. 나머지 3건은 아직 미검토)
- (c) 아무 조치 없이 4차 착수 시점까지 미룬다

**개발 측 권고**: (b). N6으로 오매칭이 이미 1건 실증됐고, 검토 안 된 3건(`물류관제_260715`·`출하조_260715_134802`·`공정조_2026.07.16`)이 남아 있다 — 제목이 D'Flow와 일치하는 것으로 1차 확인은 됐으나(`prod-survey-2026-07-27.md` §3 "claim 연결분 5건의 제목 일치 점검" 표) 내용까지 사람이 확인한 것은 아니다. 4차 착수 전에 한 번 훑어두면 자동 링크 설계(대상 1 판정 기준 등) 논의가 더 근거 있게 진행된다.

**기한·소유자**: 급하지 않음(4차 착수 전까지). ⚠️ 확인 필요

## 6. (신규) §2-E ⑥ 해소 여부 — D'Flow가 인지하고 있는지 확인 필요

**무엇을 정해야 하나**: 정본 §2-E 표 6번 항목은 "배치 `items[].folder_path` 타입 오류가 현재 구현에서 **요청 전체 400**이라 계약과 어긋난다 — **코드 결함 수정 필요**"라고 적어 뒀다(`decisions-final-2026-07-27.md` §2-E). 그런데 소스 조사 결과 D'Flow 브랜치 HEAD(`94e5eca`)의 **실제 코드는 이미 건별 실패로 동작**한다 — `folder_path`/`team` 타입 오류 1건이 나머지 199건을 막지 않는다(`dflow-source-findings-2026-07-28.md` §2). v2.4 계약 문언도 이를 "봉투 400의 범위를 정확히 열거"하는 조항(§4c.1)으로 반영해 뒀다(`dflow-contract-v23-delta-2026-07-28.md` §2 6번 행). **D'Flow가 이 사실을 인지하고 결정 문서(§2-E)를 갱신했는지는 확인되지 않았다** — 소스만으로는 "어느 커밋에서 언제 고쳐졌는지" diff 추적도 하지 않았다(`dflow-source-findings-2026-07-28.md` §「소스로도 확정 못 한 것」).

**왜 지금 필요한가**: 항목 2가 승인되면 `W12`·`W13`을 "이 결함은 이미 해소됐다"는 전제로 코딩하게 된다. D'Flow의 공식 인지가 갱신되지 않은 채 정식 v2.4가 송부되면, D'Flow 쪽 결정 문서(§2-E)와 실제 구현·우리 코딩 전제가 서로 다른 상태로 굳을 수 있다 — 나중에 "이게 왜 아직 결함 목록에 남아 있냐"는 혼선이 생긴다. 급하지는 않다(우리 쪽 코딩·검증을 막지 않으므로) — 회신문 전달(항목 1) 시 확인 문구를 하나 얹으면 비용이 거의 없다.

**선택지**:
- (a) 회신문(항목 1) 전달 시 "§2-E ⑥은 브랜치 HEAD에서 이미 건별 실패로 동작함을 확인했습니다. 결정 문서 갱신이 필요한지 확인 부탁드립니다"를 추가 확인 요청으로 얹는다
- (b) 별도로 확인하지 않고, 재편철 코딩·검증(실제 dry-run 실측)에서 자연히 드러나게 둔다

**개발 측 권고**: (a). 회신문이 어차피 나갈 예정이라(항목 1) 추가 비용이 거의 없다. 다만 **회신문 자체(`ddobak-reply-2026-07-27.md`)를 고치는 것은 이 문서의 권한 밖**이다 — 팀장이 전달자에게 이 확인 문구 추가를 지시할지만 정하면 된다.

**기한·소유자**: 회신문 전달(항목 1)과 동시. ⚠️ 확인 필요
