## 1. 회신문 전달 — 누가, 언제 D'Flow에 보내나

**무엇을 정해야 하나**: `ddobak-reply-2026-07-27.md`(170행, 정본 §7 11건 전항목 답변 + 신규 발견 N5·N6 + 요청사항 6건)를 누가 D'Flow에 전달하고 언제 보낼지.

**왜 지금 필요한가**: 이 문서가 D'Flow와의 유일한 통신 채널이다. 계약 v2.4 요청(#2), R1 일정 확인 요청(#3), claim 오매칭 통보(N5·N6, #9)가 전부 이 문서 안에 있다. 안 보내면 D'Flow는 이 내용을 모른 채로 남는다.

**선택지**:
- (a) 팀장이 직접 D'Flow 담당자(PMO)에게 전달
- (b) 개발 측이 기존 커뮤니케이션 채널로 전달(⚠️ **채널 자체가 확인 안 됨** — 이전 왕복이 어떤 경로로 이뤄졌는지 자료에 명시가 없다)

**개발 측 권고**: 없음(전달 경로는 팀장 소관). 다만 **이 문서가 안 보내지면 하위 2~3·9번 항목은 팀장이 아무리 빨리 결정해도 D'Flow 쪽 착수가 못 시작한다** — 우선순위 1순위로 처리 권고.

**기한·소유자**: ⚠️ 확인 필요 (전달자 미지정)

## 2. 계약 v2.4 미수령 — 요청 소유자·기한

**무엇을 정해야 하나**: D'Flow가 계약서 v2.4(§4c.5 조상 규칙 개정, `folder_path_status` 신설, 배치 에러 매핑 등 9건, `decisions-final-2026-07-27.md` §2-E)를 언제까지 보내도록 누가 요청·독촉할지.

**왜 지금 필요한가**: `ddobak-W12`·`W13`(재편철 배치 코드)이 **코딩할 계약 자체가 없어** 착수 불가 상태다(`handoff-2026-07-27.md` §5 "막힌 것" 표). `ddobak-W18`(계약 사본 동기화, 0차)도 같은 이유로 블록. 재편철 1회차(dry-run·APPLY) 전체가 이 뒤에 걸려 있다.

**선택지**:
- (a) D'Flow에 개발 측 회신문(#1)으로 요청만 하고 회신 대기(수동적)
- (b) 팀장이 D'Flow PMO에게 별도로 기한을 못 박아 요청(능동적)

**개발 측 권고**: (b), 단 기한은 작업량을 감안해 잡을 것. `dflow-W8`(계약 개정) **완료는 v2.3까지**(커밋 `4387576`, `decisions-final-2026-07-27.md` §2-E)다. **또박또박에 송부할 v2.4는 아직 만들어지지 않았다** — 같은 §2-E가 "아직 또박또박에 송부하지 않았으므로, 아래를 반영한 v2.4를 한 번에 송부한다"며 반영 항목 9건을 표로 명시해 뒀다. 그중 **문서만 고치면 되는 것은 3건**(`from` nullable 명시·`linked=true` 순회 규약·플래그 전환 규약 명문화)이고, **나머지 6건은 D'Flow 쪽 코드 변경까지 필요**하다(조상 규칙 개정·`folder_path_status` 신설·`pmo_admin` 게이트·폴더 개명 비전파+NFC 정규화·비활성 팀 500→400 매핑 5건은 "계약+코드", 배치 타입오류 건별 실패 매핑 1건은 "코드 결함 수정"). 즉 **"보내기만 하면 되는" 상태가 아니다** — "내일까지" 같은 촉박한 기한은 비현실적이고, 위 6건의 코드 반영 규모를 근거로 기한을 제시할 것.

**기한·소유자**: ⚠️ 확인 필요 (자료에 기한 명시 없음)

## 3. D'Flow R1~R3 배포 일정 확보 — 소유자

**무엇을 정해야 하나**: D'Flow의 R1(플래그 `false` 배포)·R2(플래그 `true` 전환)·R3(연결 초기화) 각각의 확정 날짜를 누가 받아올지.

**왜 지금 필요한가**: 정본 §0에 "R1은 검증 종료 즉시 배포(**날짜 미확정** — 확정되면 별도 통보)"라고만 돼 있다(`decisions-final-2026-07-27.md`). 재편철 1회차 APPLY는 배치 엔드포인트(`dflow-W6`)가 R1에 포함되므로 R1 배포 전엔 실행 불가. `ddobak-W14`의 `include_archived` 동작도 R1 배포 전엔 실사용 검증이 안 된다(회신문 5번 "R1 배포 일시 통보" 요청과 동일 사안).

**선택지**:
- (a) D'Flow의 별도 통보를 기다린다(수동)
- (b) 팀장이 D'Flow PMO 카운터파트에게 직접 일정을 확인한다(능동)

**개발 측 권고**: (b). 재편철 1회차·2차 배포 창(#4)이 전부 이 날짜에 종속돼 있어, 알 수 없는 상태로 두면 우리 쪽 준비(수작업 A~D, #5~8)를 언제 마쳐야 하는지도 정해지지 않는다.

**기한·소유자**: ⚠️ 확인 필요

## 4. 2차 배포 창(R2 시점) — 이미 완성된 작업이 대기 중

**무엇을 정해야 하나**: 커밋 `d0b893e7`(또박또박 2차 선구현 — 제목 접두 폐기·team 완화·폴더명/깊이 검사, `W2`·`W3`·`W4`·`W5`·`W6`)을 **언제 `main`에 머지·배포할지**를 결정하는 기준점(R2 시점)을 D'Flow와 언제 맞출지.

**왜 지금 필요한가**: 이 커밋은 **이미 완성돼 검증까지 끝났지만 배포가 금지된 상태**다(`handoff-2026-07-27.md` "⛔ `d0b893e7`은 2차분이라 `main`에 올리면 안 된다... D'Flow R2 전에 나가면 제목 접두도 없고 폴더도 안 잡힌 상태가 된다"). R2 이전에 배포하면 회귀가 발생하는 반면, R2가 언제인지는 #3(D'Flow 일정)에 종속돼 있다. 완성된 자산이 대기 상태로 오래 머물수록 브랜치 드리프트·재검증 비용이 커진다.

**선택지**:
- (a) #3이 해소될 때까지 대기(현재 상태 유지)
- (b) 팀장이 "R2 준비 완료" 통보를 D'Flow에 선제적으로 보내(정본 §2-A 조건 ③ "또박또박 2차 배포 준비 완료 통보") D'Flow의 R2 결정을 앞당기도록 유도

**개발 측 권고**: (b) 병행. 정본 §2-A는 플래그를 `true`로 돌리는 조건 3가지 중 하나로 "또박또박 2차 배포 준비 완료 통보"를 명시한다 — **이 통보 자체를 우리가 먼저 보낼 수 있다.** 다만 조건 ①(재편철 1회차 APPLY 완료)·②(19건 대조표 정리 완료)가 아직이므로, 통보만으로 R2가 즉시 열리진 않는다.

**기한·소유자**: #3과 동일 — ⚠️ 확인 필요

## 5. 수작업 A — 폴더명 통일 (`ERP/영업` vs `ERP/영업팀`)

**무엇을 정해야 하나**: 또박또박 `ERP/영업팀`과 D'Flow `ERP/영업` 중 어느 이름을 정본으로 할지.

**왜 지금 필요한가**: 재편철 1회차 APPLY보다 **반드시 먼저** 끝나야 한다(`manual-worklist-2026-07-28.md` §A). 안 하면 배치가 D'Flow에 `영업팀` 폴더를 새로 만들어 같은 조직의 폴더가 2개 생긴다.

**선택지**:
- (a) `영업`(D'Flow 이름)으로 통일 — 또박또박에서 개명 1건만 하면 끝
- (b) `영업팀`(또박또박 이름)으로 통일 — D'Flow 쪽도 개명 필요, **개명은 전파되지 않으므로**(`decisions-final-2026-07-27.md` §2-E ⑧) D'Flow가 별도로 손대야 함

**개발 측 권고**: (a). 회신문(`ddobak-reply-2026-07-27.md` "또박또박이 D'Flow에 요청하는 것" 2번)에서 이미 "D'Flow 선호가 없으면 저희가 정하겠다"고 통보해 두었다 — (a)가 조치 비용이 더 싸다. **다만 이 결정은 회신문이 실제로 전달돼야(#1) D'Flow가 반대할 기회가 생긴다.**

**기한·소유자**: 재편철 1회차 APPLY 전까지. 소유자 ⚠️ 확인 필요(또박또박 측이 정한다는 방침만 있고 담당자 미지정)

## 6. 수작업 B — 회의 4건 폴더 이동 실행 승인 (프로덕션 변경)

**무엇을 정해야 하나**: 또박또박 프로덕션에서 회의 4건(#14·#15·#17·#18 — `기타-표준화(우봉우)…` 2건, `기타-품질(김효준)…` 2건)을 `MES/기타` → `MES/조업및표준화`·`MES/품질`로 이동하는 작업을 **실행해도 되는지 승인**.

**왜 지금 필요한가**: D'Flow 제목 접두(`기타-`)가 증거로 남아 "D'Flow 사용자가 옮긴 것이 확실하고 분류가 더 정확함"이 이미 실측으로 확인됐다(`prod-survey-2026-07-27.md` §5). 즉 **방향 판단은 끝났고 실행만 남았다.** D'Flow R1을 기다릴 필요 없이 지금 해도 된다(`manual-worklist-2026-07-28.md` 상단 "전부 D'Flow R1을 기다릴 필요가 없다"). 안 옮기면 재편철 dry-run마다 이 4건이 `skipped(manual_placement)`로 계속 재보고된다.

**선택지**:
- (a) 승인하고 지금 실행
- (b) 재편철 1회차 대조·타이밍에 맞춰 나중에 실행

**개발 측 권고**: (a). 판단 근거가 이미 확정적이고, 대상 폴더 2곳 모두 또박또박에 이미 존재해 새로 만들 필요가 없다(리스크 낮음). 다만 **이것은 실서버 프로덕션 데이터 변경**이라 이 프로젝트 운영 원칙상(러닝 서버·프로덕션 직접 변경은 사용자 승인 필요) 팀장 승인 없이 개발 측이 임의로 실행하지 않았다. **실행 주체**(사람이 UI로 직접 하는지, 스크립트로 하는지)도 함께 정해야 한다 — 서브에이전트가 프로덕션에 직접 쓰기 작업을 하는 것은 이 프로젝트 운영 규칙과 상충한다.

**기한·소유자**: 재편철 1회차 dry-run 전까지 완료 권고. 소유자·실행 주체 ⚠️ 확인 필요

## 7. 수작업 C — 회의 `#1` 처리 (팀 루트 → `ERP/영업` 이동 여부 + 제목 동일성 확인)

**무엇을 정해야 하나**: 두 가지가 묶여 있다.
- **C-1**: 또박또박 `#1`(`260721_글로벌영업담당_임원_인터뷰_통합`, 현재 `ERP` 팀 루트)을 D'Flow 위치(`ERP/영업`)에 맞춰 이동할지.
- **C-2**: 애초에 이 매칭이 맞는지 — 또박또박 제목이 `..._AS-IS`, D'Flow 제목이 `..._통합`으로 **다르다.**

**왜 지금 필요한가**: C-1은 조상 규칙(정본 §2-J)상 자동으로 안 고쳐진다 — 현재 위치(`ERP`)가 목표(`[ERP]`)의 자손이라 배치가 보호해 `skipped(manual_placement)`로 계속 남는다. 그런데 C-2가 안 풀리면 C-1을 실행하는 것 자체가 **오매칭을 고착시킬 위험**이 있다 — 이 연결은 `claim`(자동 매칭이 아니라 수동 연결)으로 만들어졌고, 같은 세션에서 `claim` 오매칭이 실제로 1건 확인됐다(id 34 건, #8·#9 참조). 즉 C-2를 먼저 확인해야 C-1을 안전하게 실행할 수 있다.

**선택지 (C-2)**:
- (a) 같은 회의다(제목만 다르게 붙었다) → C-1 그대로 진행
- (b) 다른 회의다(오매칭) → 수작업 재매칭 필요, C-1은 보류

**개발 측 권고**: 없음 — **이 판단은 회의 내용을 아는 사람만 할 수 있다**(제목 텍스트 비교로는 결론 낼 수 없음). 회신문에서도 "PMO 확인 요청"으로 남겨 뒀다.

**기한·소유자**: C-2가 먼저, 그다음 C-1. 재편철 1회차 대조 전까지 권고. 소유자 ⚠️ 확인 필요

## 8. 수작업 D / 미결 — 고아 레코드(D'Flow `#7`) 관련 `id 34` 복원 여부

**무엇을 정해야 하나**: 또박또박에서 소프트 삭제된 `id 34`(`원료팀 2026.07.08`)를 복원할지 여부. D'Flow 쪽 `#7`(`원재료_2026.07.15_11시00분`, `019f87db-c94d`)은 **삭제하지 않는다**(사용자 결정, 2026-07-28, 예외 없음)로 이미 확정됐고 이 항목은 그와 별개다.

**왜 지금 필요한가**: 급하지 않다 — 재편철 1회차 `items`에서 이 건은 이미 제외돼 있어(원본이 삭제돼 목표 경로를 만들 수 없음) 1회차 실행을 막지 않는다. 다만 데이터 정합성 이슈로 계속 남는다.

**선택지**:
- (a) **미복원(현행 유지)** — `id 34`는 삭제 상태로 두고, D'Flow `#7`도 고아인 채로 둔다. 추가 조치 없음
- (b) **복원** — `id 34`를 되살리면 D'Flow `#7`이 재편철 대상에 정상 편입된다. 단 **`claim` 자체가 오매칭이었으므로**(`id 34` = 07/08 녹음 55분짜리 회의, D'Flow `#7` = 07/15 회의로 서로 다른 회의) 복원해도 문제가 자동으로 풀리지 않는다 — 연결을 끊고 사람이 재매칭까지 해야 실익이 생긴다

**개발 측 권고**: (a). 복원 자체가 오매칭을 해소하지 않고 오히려 "복원 + 재매칭"이라는 추가 작업만 만든다(`prod-survey-2026-07-27.md` §3 조치 권고). 다만 **삭제 금지 정책의 취지(무엇도 잃지 않는다)에는 (b)가 더 부합**하므로, 최종 판단은 팀장 몫으로 남긴다.

**기한·소유자**: 급하지 않음(1회차를 막지 않음). ⚠️ 확인 필요

## 9. 정책 판단 — `claim` 오매칭 위험 대응 (N5·N6)

**무엇을 정해야 하나**: 실측이 드러낸 두 가지 위험에 대해 운영 정책을 확정할지.
- **N5**: `dflow_synced_at`이 비어 있는데 이미 D'Flow에 연결된 회의가 4건 있다(id 36·38·45·87 — `meeting_dflow_controller.rb#claim`이 `dflow_url`만 갱신하고 `dflow_synced_at`은 안 채우는 정상 동작의 부작용). 향후 자동 링크(4차)가 이 4건을 "한 번도 안 올라간 회의"로 오판하면 **다른 회의록에 재연결 → 고아 + 오매칭**이 생긴다.
- **N6**: `claim` 오매칭이 **이미 실제로 1건 발생**했다(`id 34` 건). 정본 §6("자동 링크 v1은 자동 claim을 끄고 사람 승인만 허용")의 근거가 실증됐다.

**왜 지금 필요한가**: 급하지 않다 — 4차(`ddobak-W15`·`W16`, 자동 링크)는 D'Flow R3(연결 초기화)가 먼저 나와야 착수 가능해 아직 멀었다. 하지만 **지금 명문화해 두지 않으면 4차 착수 시점에 다시 논쟁**이 된다.

**선택지**:
- (a) 정본 §6의 "자동 claim 금지, 사람 승인만" 결정을 **그대로 4차 착수 조건에 못 박는다** — 추가 조치 없음(이미 정본에 있음, 재확인만)
- (b) (a)에 더해, 현재 `claim`으로 연결된 5건(N5의 4건 + 삭제된 id 34) 전체를 **4차 착수 전에 미리 사람이 재검증**한다(#7 이미 오매칭 확정, `#1` 확인 대기 중(#7 항목), 나머지 3건은 아직 미검토)
- (c) 아무 조치 없이 4차 착수 시점까지 미룬다

**개발 측 권고**: (b). N6으로 오매칭이 이미 1건 실증됐고, 검토 안 된 3건(`물류관제_260715`·`출하조_260715_134802`·`공정조_2026.07.16`)이 남아 있다 — 제목이 D'Flow와 일치하는 것으로 1차 확인은 됐으나(`prod-survey-2026-07-27.md` §3 "claim 연결분 5건의 제목 일치 점검" 표) 내용까지 사람이 확인한 것은 아니다. 4차 착수 전에 한 번 훑어두면 자동 링크 설계(대상 1 판정 기준 등) 논의가 더 근거 있게 진행된다.

**기한·소유자**: 급하지 않음(4차 착수 전까지). ⚠️ 확인 필요
