## B-2 · B-3 · C-2 — 하나의 결정

### 결정: **재편철(또박또박 3차)을 전송 전환(2차)보다 앞세운다.**

### 왜 (b)인가

**(a)안(판정 기준 교체)의 비용이 실질적으로 높다.** "마지막 전송 이후 D'Flow 쪽 이동이 있었나"를 판정하려면 이동 시각·주체 흔적이 필요한데, `minutes.updated_at`은 외부 전송으로도 갱신되므로 그대로는 못 쓴다. 새 컬럼이나 이력 테이블이 필요하고, 이건 "스키마 마이그레이션 없음"이라는 이번 작업의 전제(D'Flow §5)를 깬다.

**(b)안은 지금 공짜다.** wbs-web `main`에 `folder_path` 커밋이 0건이라 D'Flow 릴리스 순서를 자유롭게 짤 수 있다. `dflow-W6`(배치 엔드포인트)는 어차피 `dflow-W2`(`resolveFolderPath`)에 의존하고, `dflow-W3`(신규 전송 전환)도 같은 `W2`에 의존한다 — **즉 `W2` 다음에 `W6`을 먼저 낼지 `W3`을 먼저 낼지의 문제일 뿐, 추가 작업이 없다.**

### 왜 이게 문제를 실제로 없애나

`manual_placement` 판정의 전제는 "팀 루트에 있으면 외부 API가 자동 편철한 것"이다. 이 전제는 `dflow-W3` **이전 세계에서만 참**이다. 3차를 W3보다 앞세우면:

- 재편철 시점에 기존 전송분은 **전부 팀 루트에 평평**하다 → 전제가 참 → 오분류 0
- 재편철 후 2차가 나가면 신규 전송이 하위 폴더로 직접 간다 → 그때부터는 재편철이 필요 없다

### 잔여 창(window)과 그 처리

3차 실행 ~ 2차 배포 사이에 새로 전송된 회의는 다시 팀 루트에 평평하게 안착한다(그 구간엔 `dflow-W3`가 없어 `insertNew`가 여전히 `resolveTeamRootFolderId`를 쓴다). → **2차 배포 직후 재편철을 한 번 더 돌린다.**

2회차 실행이 안전한 이유 — **두 부류가 각각 다른 이유로 안전하다. 섞어 읽지 말 것**:

| 부류 | 2회차에서 | 왜 안전한가 |
|---|---|---|
| **창(3차~2차) 전송분** | `moved` | 팀 루트에 평평하므로 §8.3 판정표 **2행("팀 루트 = 자동 편철")이 그대로 참**이다 → 정상 이동. `already_correct`와 무관 |
| **2차 이후 전송분** | `already_correct` | 자동 편철로 이미 **현재 위치 = 목표 위치**다. `already_correct`가 `manual_placement`보다 **먼저** 판정되므로(D'Flow §8.2-10) 오분류가 구조적으로 불가능 |
| **1회차에 옮긴 건** | `already_correct` | 위와 동일 |

- 재편철은 **멱등**이다(D'Flow §8.2-7)
- `updated_at` 미갱신·버전 append 없음이라 2회 돌려도 사용자에게 "수정됨"으로 안 보인다

**잔여 리스크 1건**: 2차 이후 사용자가 또박또박에서 회의를 옮기고 **재전송은 안 한 채** 2회차 재편철을 맞으면 `manual_placement`로 skip된다. 이 건은 사용자가 재전송하면 해소된다(D1=B — 재전송이 위치의 SSOT). 수백 건 규모가 아니라 개별 건이므로 수용 가능.

### B-3에 대해 — 같은 결정

자유 루트 회의(루트가 팀코드가 아닌 것)는 **오늘도 전송에 성공하고 있고**, `replace`가 `folder_id`를 갱신하지 않아 **최초 전송 위치가 영구 고정**된다. 이건 `ddobak-W3`와 무관하게 이미 라이브다.

- **(a) UI 보류를 기각하는 이유**: 사용자의 정상 업무를 막는다. 그리고 "얼마나 오래 막을지"가 D'Flow 일정에 달려 있어 통제 불가다
- **(b)를 택하면**: 그 기간 쌓인 것을 3차가 정리한다. 3차가 앞으로 오면 **보류 기간이 짧아진다** — (b)의 약점이었던 "정리가 언제 오나"가 함께 해소된다

⚠️ **단 조건**: (b)는 **3차 실행이 확정될 때만** 성립한다. 3차를 안 하면 자유 루트 회의는 영구히 평평하게 남는다.

### C-2에 대해 — 자동으로 따라온다

D'Flow §6 D&D를 3차보다 먼저 내면 사용자들이 정리 차원으로 회의록을 옮기고, 3차가 그것을 전부 `manual_placement`로 skip해 **부분 일치가 '완료'로 보고**된다. 3차가 앞으로 오면 이 창 자체가 생기지 않는다.

→ **D'Flow §6(W18~W23)은 3차 완료 후 배포.**

## B-4 — archived 오진

### 결정: **(a) D'Flow가 보관 상태를 구분 노출한다.** (b)는 이미 잠정 적용됨

### 왜 (a)인가

(b)만 하면 **오진은 못 없애고 사용자에게 전가**한다. 구체적으로:

1. 사용자는 "D'Flow에서 확인되지 않습니다"를 보고 두 갈래를 안내받는데, 보관분에서는 **둘 다 실패한다** — [찾기]는 보관분이 `linked=false` 목록에 없고, [새로 전송]은 409 `archived`로 막힌다
2. 진짜 해법("D'Flow에서 보관 해제")은 (b)로 문구에 넣을 수 있지만, **사용자가 D'Flow 권한이 없으면 스스로 못 한다**
3. **자동 링크가 계속 오분류한다** — `RELINK_RESET=1` 경로에서 보관분이 '초기화분'으로 분류돼, D'Flow에 원본이 살아 있는데 엉뚱한 회의록을 재claim하러 간다. 문구 수정으로는 이게 안 잡힌다

(a)의 비용은 **기존 라우트에 파라미터 하나**다(`include_archived=true` 또는 `external_id` 정확 조회 시 archived 필터 해제 + 응답에 `archived: true`). "신규 엔드포인트는 1개뿐"이라는 D'Flow §5 방침과 충돌하지 않는다. D'Flow 지시서 자신도 (a)를 권고한다.

### 조치

- D'Flow: `GET /api/v1/minutes`의 `external_id` 정확 조회에서 archived를 배제하지 않고 응답에 상태를 실어준다
- 또박또박: 현재 (b)로 잠정 적용된 문구("확인되지 않습니다(초기화·보관·삭제 중 하나)")를 **보관/초기화 구분 문구로 세분화**한다. `ddobak-W14` 범위 안
- 자동 링크: 보관분을 후보·대상 양쪽에서 제외

## B-5 — 깊이 초과

### 결정: **절단 유지 + 또박또박이 전송 전 경고(차단 아님) + 응답 에코 표시.** D'Flow 변경 0

### 왜 400 거절이 아닌가

일관성만 보면 60자와 같이 400이어야 한다. 하지만 두 축은 성질이 다르다:

| | 폴더명 60자 초과 | 깊이 5 초과 |
|---|---|---|
| 사용자의 해결책 | **이름을 줄인다** — 쉽고 국소적 | **폴더 구조를 재편한다** — 조직 체계를 바꾸는 일 |
| 거절의 대가 | 낮음 | **정당한 5단 이상 구조를 쓰는 팀이 전송을 아예 못 한다** |

또박또박은 폴더 깊이가 무제한이고 "폴더 구조는 자유"가 이번 설계의 전제(D4)다. 깊이로 전송을 막으면 그 전제를 스스로 무너뜨린다.

### 왜 현행 유지도 아닌가

현행의 진짜 문제는 절단 자체가 아니라 **조용하다는 것**이다. `신규TF/A/B/C/D1`과 `…/D2`가 한 칸 내림 후 6단이 되면 둘 다 `MES/신규TF/A/B/C`로 병합되는데 에러도 경고도 없다.

### 제3안 — 또박또박이 자기 쪽에서 경고한다

**또박또박은 자기 폴더 깊이를 이미 안다.** D'Flow 호출이 전혀 필요 없다:

```
편철 예정 깊이 = folder_path.length + (루트가 팀코드면 0, 아니면 1)
> 5 이면 다이얼로그에 경고 — "D'Flow는 5단까지만 저장합니다.
  <절단 후 경로>로 편철되며, 같은 5단이 되는 다른 폴더와 합쳐질 수 있습니다."
```

- **차단하지 않는다** — 사용자가 인지하고 보낸다
- `ddobak-W4`(61자 사전 검사)와 **같은 검사 지점**이라 추가 비용이 거의 없다
- `ddobak-W7` 미리보기가 지금 **절단 전** 경로를 보여주는 문제(오해를 굳힌다)도 같이 해소된다
- 사후 확인은 `ddobak-W8` 응답 에코가 담당 — 이미 ✅ 필수로 승격됨

⚠️ **경고를 띄우는 시점 주의** — 다이얼로그 열자마자가 아니라 **team 확정 후**다.
`+1`(한 칸 내림) 여부는 루트가 팀코드인지에 달렸는데, 자유 루트일 때 `detectDflowTeam`은 `null`을 반환하고
사용자가 셀렉트에서 team을 고른 뒤에야 `+1`이 확정된다. 다이얼로그 open 시점에 계산하면
**경고가 가장 필요한 경우(자유 루트 = `+1`이 붙어 깊이를 하나 더 먹는 경우)에 조용히 안 뜬다.**
→ 경고는 `teamOverride` 확정 이후 재평가되어야 한다.

→ **`ddobak-W4`·`ddobak-W7` 범위에 깊이 경고를 추가한다.** 워크리스트 수정 2줄.

## B-1 — 미분류 폴백 응답값

### 결정: **`folder_path: null`** (D'Flow §3.3 제안 확정)

`[]`는 "팀 루트에 편철 **성공**"이라는 유의미한 값이다(3값 규약). 미분류(`folder_id: null`)를 `[]`로 표현하면 또박또박이 규약대로 "팀 루트에 편철됨"이라고 **정반대 안내**한다. `null`로 구분하는 것이 옳다.

- 또박또박은 이미 방어돼 있다 — 판정을 `folder_id === null`로 걸어서 이 결정이 어느 쪽이든 **동작은 옳다**. 타입만 확정하면 된다(`ddobak-W9`)
- 리스크 낮음. D'Flow 제안을 그대로 승인하면 된다

## A-3 — 계약서 개정

### 결정: **`dflow-W8`을 D'Flow 최우선 단독 선행으로 낸다. 범위는 §3·§8·§9.**

- 두 사본이 이미 21행 갈라졌고 **둘 다 `folder_path` 0건**이며, 이번 변경과 **정면 충돌하는 문장 3개**(`§0 D10` 제목 접두 / `§4.2` 필드표 / `§4b` "해제 API 없음")가 살아 있다
- §3만 개정하면 `POST /minutes/folder`(§8)와 연결 초기화(§9)가 계약 SSOT에 안 실린다. **`ddobak-W12`·`W13`이 그 엔드포인트를 직접 호출**하므로 3차 착수 전에 반드시 필요
- 정본은 **wbs-web v2.2**. 또박또박 사본이 뒤따라 동기화(`ddobak-W18`, **0차**). **반대 방향 금지**

## A-1 — D'Flow 작업 순서 (권고)

일정은 팀장 권한이지만, 위 결정을 반영한 **순서**는 아래가 유일한 정합 배열이다.

```
① dflow-W8   계약서 개정 (§3·§8·§9)          ← 착수 전 선행, 단독
② dflow-W1   payload 파싱 (+W1-b team 검증)
   dflow-W2   resolveFolderPath               ← W3·W6이 공유
③ dflow-W6   POST /minutes/folder (배치)
   ────────── 또박또박 0차(W18) · 3차(W12·W13) 실행 ── 재편철 1회차
④ dflow-W3   insertNew 전환
   dflow-W4   응답에 folder_id·folder_path
   dflow-W5   replace의 folder_id 갱신
   ────────── 또박또박 2차 (W2·W3·W4·W5·W6·W7·W8·W19) ──
   ────────── 재편철 2회차 (창 정리, already_correct로 안전) ──
⑤ dflow-W10  연결 초기화 + 식별자 표시
   ＋ B-4 (a) archived 구분 노출
   ────────── 또박또박 4차 (W15·W16) ──
⑥ dflow-W18~W23  폴더 중심 UI 재편 (D&D)     ← 3차 완료 후 (C-2)
```

**또박또박 1차-a(완료)·1차-b(W14·W17)는 D'Flow 의존이 0이라 언제든 나갈 수 있다.**
단 `ddobak-W14`는 **`dflow-W10`보다 반드시 먼저** — 그 사이 창이 열리면 중복 회의록이 생기고 자가 치유되지 않는다.

## A-2 — `0043` 적용 확인 (권고)

**결정이 아니라 사실 확인이다. 착수 전 필수.**

미적용이면 팀 루트 폴더 자체가 없어 **현재 또박또박 전송분이 전부 미분류로 쌓이고 있을 수 있다.** 그 상태에서 재편철을 돌리면 전건 `failed(no_team_root)`가 나온다.

→ **미적용으로 확인되면 이 작업 전체를 보류하고 `0043` 적용을 먼저 한다.**

```sql
select name, sort, parent_id, created_by from minute_folders
where parent_id is null order by sort;
-- 기대: PMO(0)·ERP(1)·MES(2)·가공(3)·MDM(4), created_by 전부 null

select count(*) from minutes where folder_id is null and archived_at is null;
-- 기대: 0에 가까움. 크면 0043 미적용 또는 백필 누락
```

⚠️ **이건 승인이 아니라 누군가 실제로 실행해야 하는 항목이다.** 실행 주체를 지정하지 않으면 "승인됨" 상태로 남은 채 아무도 안 돌린다. 운영 DB 접근 권한이 있는 사람이 필요하다.

## C-1 — `ACTOR_EMAIL` 계정 (권고)

### 권고: **`pmo_admin` 권한을 가진 실명 담당자 계정 — 단 이것은 해결이 아니라 차악이다**

전용 서비스 계정의 문제는 일회성이 아니라 **영구적**이다:

- 재편철이 만드는 폴더 트리 전체의 `created_by`가 그 계정이 된다
- D'Flow는 `created_by`를 폴더 개명·삭제 권한의 근거로 쓴다 → **일반 사용자가 자기 팀 폴더를 손댈 수 없게 된다.** `pmo_admin`만 가능
- 재편철은 한 번이지만 그 폴더들은 계속 남는다

실명 계정의 단점(대량 작업이 한 사람 이름으로 찍힘)은 감사 관점에서는 오히려 장점이다.

⚠️ **하지만 소유권 문제가 해결되는 것은 아니다.** 실명 계정으로 돌려도 그 폴더들은 **그 한 사람 것**이지
**팀 것이 아니다.** 팀원들은 여전히 자기 팀 폴더를 개명·삭제할 수 없고, 그 한 사람 또는 `pmo_admin`에게 요청해야 한다.
전용 서비스 계정보다 나은 점은 "최소 한 명의 사람이 손댈 수 있다"뿐이다.

→ **진짜 해법은 D'Flow 폴더 권한을 `created_by` 기반에서 떼어내는 것**이고, 이건 **별건 티켓**이다.
이번 결정은 그때까지의 임시 조치로 승인해야 한다 — 소유권 문제가 닫혔다고 보면 안 된다.

**확인할 것**: 그 계정이 D'Flow `auth.users`에 실재하는지. rake는 배치 시작 전에 빈 `items` + `dry_run` 프로브로 검증하므로, 없으면 1건도 보내기 전에 중단된다.
