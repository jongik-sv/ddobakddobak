## 3. `include_archived=true` 반영 3곳 (status 호출 / `linked=true` 순회 / 자동 링크 제외)

**답: ①·③ 완료, ② 미구현(4차 요건으로 등재).**

- **① `dflow/status` 존재 확인 호출** — **완료.** `meeting_dflow_controller.rb`의 `status` 액션이 `list_minutes(external_id:, include_archived: true)`를 호출하도록 반영했습니다. 응답에 `dflow_archived`를 추가했고, `item.key?("archived")`일 때만 채웁니다(R1 이전 구버전 응답이면 키 자체를 넣지 않습니다 — 오진 방지).
  프런트: 보관분이면 "덮어씁니다" 안내를 띄우지 않습니다(그대로 두면 409로 막히므로 거짓 안내가 됩니다). 대신 "D'Flow에서 보관됨" 안내로 분기합니다. **[전송] 버튼 자체는 막지 않습니다** — D'Flow의 409 응답이 "보관된 회의록입니다. 복원 후 다시 시도하세요."를 정확히 실어 주므로, 저희가 선차단하면 그 안내로 갈 길이 없어지고, 방금 보관 해제한 경우엔 stale 상태로 사용자가 락아웃되기 때문입니다.

- **③ `ddobak-W14` 문구 세분화** — ①과 함께 **완료.** `exists_on_dflow: false` ∧ `dflow_synced_at` 존재 조건에서 "D'Flow에서 확인되지 않습니다(초기화·보관·삭제 중 하나)" 안내 + [전송] 차단 + 갈래 2개(재연결 / 확인 후 새로 전송)로 나눴습니다.

- **② `linked=true` 페이지 순회에도 `include_archived=true`** — **미구현.** 자동 링크 감지 자체가 4차(`ddobak-W15`·`W16`) 요건이라 그때 함께 등재했습니다. 참고로 **`linked=false`(연결 후보 조회)에는 의도적으로 켜지 않기로 규약을 명시**했고, 조회 프록시의 파라미터 화이트리스트에도 일부러 넣지 않았습니다 — 살아 있는 유일한 호출자가 `linked=false` 후보 검색이라, 켜는 순간 "보관분이 claim 후보로 노출되는" 금지 조합이 열리기 때문입니다.

**검증**: rspec **134 pass** · `tsc -p tsconfig.app.json` **0** · vitest **45 pass**(전체 스위트 1816 pass) · rubocop/eslint clean.

＋ 배포 후 자체 적대 리뷰에서 저희 쪽 회귀 1건을 잡아 고쳤습니다(`0852ac4b`) — `status` 액션이 `items`를 배열로 가정해, 비배열 응답이 오면 `exists_on_dflow`를 오판정하고 500을 냈습니다. **D'Flow 측 조치는 없습니다** — 계약상 `items`는 항상 배열이며, 저희 쪽 방어가 빠져 있었을 뿐입니다.

## 4. `ddobak-W9` 응답 타입 nullable 확정

**답: 확정.**

`folder_id`·`folder_path` 둘 다 nullable로 반영했습니다. 다만 필수(non-optional)가 아니라 **optional까지 허용**합니다 — 오늘 응답엔 이 두 키가 아예 없어서(`undefined`), 필수로 고정하면 `dflow-W4` 배포 전 구간에서 저희 프런트가 깨집니다. 배치 응답의 `from: string[] | null`도 같은 방식으로 수용할 예정입니다(배치 타입 자체는 3차 `ddobak-W12`·`W13`에서 생성).

**근거**: 정본 §2-D의 nullable 규약을 그대로 따릅니다. 판정은 `folder_path`가 아니라 **`folder_id === null`** 로 합니다 — `null`(미분류)과 `[]`(팀 루트 편철 **성공**)를 뭉개면 사용자 안내가 정반대가 되기 때문입니다.

### (가) §7-9 확장이 실측과 충돌합니다 — 대상 1 판정 기준 재정정 필요

`dflow_synced_at`이 NULL인데 **이미 D'Flow에 연결된** 회의가 **4건**(＋삭제분 1건) 있습니다(id 36·38·45·87, ＋삭제된 id 34).

### (나) `claim` 오매칭이 이미 1건 발생했습니다

## 「또박또박이 D'Flow에 요청하는 것」

1. **고아 레코드 처리** — `019f87db-c94d`(#7). 저희 쪽에 대응 회의가 없습니다(원본 id 34가 소프트 삭제됨). **삭제하지 마십시오.** 또박또박 정책상 양 시스템 모두 회의(회의록) 삭제를 금지합니다 — 예외 없음. D'Flow에 요청드리는 것은 **그대로 둘 것** 뿐입니다. 본문이 원래 수동 업로드분이라 내용 보존 가치도 있습니다. 참고로 저희 쪽 재편철 1회차 `items`에서는 #7을 제외해 두었습니다(목표 경로를 만들 원본이 없어서이며, 삭제 권고가 아닙니다).
2. **폴더명 통일** — D'Flow `ERP/영업` vs 저희 `ERP/영업팀`. **또박또박 측에서 통일합니다** — PMO 회신을 기다리지 않고 저희가 정본 이름을 정해 맞추겠습니다. 선호하시는 이름이 있으면(`영업` 또는 `영업팀`) 알려 주십시오 — 없으면 저희가 정합니다. ⚠️ 이 통일은 **재편철 1회차보다 먼저** 끝내야 합니다 — 안 그러면 배치가 D'Flow에 `영업팀` 폴더를 새로 만들어 중복 폴더 2개가 됩니다.
3. **#1 매칭 정합성 확인** — `_AS-IS` vs `_통합`이 같은 회의인지 확인 부탁드립니다.
4. **계약 v2.4 송부** — `ddobak-W18`(0차)이 대기 중입니다. 이게 없으면 저희 3차 착수가 불가합니다.
5. **R1 배포 일시 통보** — `include_archived`·`archived` 검증이 R1 이후에만 가능합니다.
   ＋ **한 줄 확인 요청**: R1 **이전** 버전의 `GET /api/v1/minutes`가 **미지 쿼리 파라미터를 조용히 무시**합니까(400을 내지 않습니까)?
   저희 `status` 액션이 이제 `include_archived=true`를 **무조건** 실어 보냅니다. 만약 구버전이 400을 낸다면 `public_uid`가 있는 **모든 회의의 상태 조회가 깨집니다.**
   정본 §3 제약 ①(`dflow-W24 ≤ ddobak-W14`)이 이미 R1 선행을 강제하므로 순서를 지키면 문제가 없고, 저희도 그 순서로 배포할 예정입니다. 다만 배포 사고에 대비해 **무시된다는 확인**만 받아 두고 싶습니다(무시된다면 저희 쪽 폴백 코드가 불필요합니다).
6. **§4-③ 사람 판정 6건** — 위 6번 항목의 성격 분석을 근거로 **또박또박이 수작업으로 매칭합니다**(PMO 판정 요청이 아닙니다). 특히 #14·15·17·18은 D'Flow 위치가 더 정확해 보이므로, 정본 §4-④에 따라 저희 쪽에서 폴더를 옮기겠습니다(D'Flow만 고치면 다음 재전송에 다시 덮이므로). 매칭이 끝나는 대로 **결과를 통보**드리겠습니다 — 회신 대기 없이 진행합니다.
